# 菇点、活动与收费规则

> 状态：个人微信内 H5 的 JSAPI 收款、主动查单和原路退款代码已实现，生产收款默认关闭
>
> 版本：2026-09-15

## 1. 产品价格

| 项目 | 价格或奖励 | 边界 |
|---|---:|---|
| 注册、登录、写日记 | 免费 | 不消耗菇点 |
| 连续完成 7 天日记 | 奖励 1 菇点 | 每个账户一次；按上海自然日的真实创建时间计算 |
| 我的七日变化分享卡 | 免费、自愿 | 分享不产生奖励，不包含日记正文 |
| 复利系统 | 10 菇点永久解锁 | 后续 AI 调用另外扣费 |
| 未解之问 | 10 菇点永久解锁 | 后续 AI 调用另外扣费 |
| 身心问题 | 10 菇点永久解锁 | 后续 AI 调用另外扣费 |
| 用户主动发起的收费 AI 调用 | 当次成功调用成本 × 2.5 | 失败输出、网络失败和系统重试不扣费 |

1 元充值等于 1 菇点。前端提供 10、20、50、100 元和 1–500 元自定义充值。内部以 `1 菇点 = 100 菇分` 的整数记账，避免浮点误差。

当前商业化分三种产品状态：

- `disabled / FREE_BETA`：H5 免费测试，不展示充值入口与收费同意，不执行功能解锁或 AI 扣费；三个高级空间对测试用户开放。页面只展示未来计划价格和渠道路线，不能让用户误以为已经收费。
- `preview / COMPLIANCE_REVIEW`：用于登录态验收价格、协议、功能门槛和钱包交互，真实支付仍关闭，不得对外作为收费产品发布。
- `live / PARTIAL_LIVE`：仅当 H5 的资质、商户配置、协议和支付验收全部通过后开放 H5 充值。微信小程序与原生 APP 不继承 H5 的支付状态，仍须分别接入小程序虚拟支付和应用商店内购。

当前渠道定位是：H5 作为免费体验与未来补充入口；微信小程序和原生 APP 作为未来主要运营入口。在对应客户端尚未开发、备案和通过支付审核前，页面可以说明计划，但不得伪造“即将开通日期”或提供绕过渠道规则的付款方式。

## 2. 七日活动与分享边界

活动资格按日记 `created_at` 转为 `Asia/Shanghai` 日期后计算。一个自然日有至少一篇未删除日记即算完成一天；修改日记或把发生日期改成过去不能补造活动天数。连续七天达到后由保存日记事务自动入账，登录较早的合格用户也可以在钱包页补领。钱包流水和活动记录共同保证幂等。

分享卡只取活动的连续天数、起止日期与产品固定文案，不取正文、心情、标签、照片、语音、AI 结论或联系人信息。微信小程序使用系统分享能力；H5 只复制可编辑的分享文案。用户不分享也获得同样奖励。

## 3. AI 扣费与 Token 展示

只有用户主动触发、标记为收费的模型请求进入扣费链路：

1. 调用前先确认用户已明确接受当前版本的收费与退款规则；未接受时返回 `402 SHROOM_BILLING_AGREEMENT`，不发起模型请求，也不扣费。随后以当前模型的高峰期、未命中缓存单价，结合本次输入字节上限和允许的最大输出 Token 计算保守授权额度；可用菇点不足时返回 `402 SHROOM_BALANCE_INSUFFICIENT`，同样不发起模型请求。
2. 供应商成功返回后，先验证输出可被业务解析，再写入不可变 AI 用量记录。
3. 根据该记录保存的公开价格快照计算人民币成本，向上取整为菇分后乘以 `2.5` 扣款。
4. 同一 AI 用量事件只允许一条钱包流水；失败输出和重试仅记录用量状态，不扣用户菇点。
5. 页面展示真实的 prompt、cache hit、cache miss、completion、total Token 与实际扣除菇点，不用“预计 Token”代替账单。
6. 授权额度只用于判断能否开始调用，不是预扣款；成功后只扣供应商返回用量对应的实际金额。如供应商异常返回导致实际金额超过已授权可用余额，差额由平台承担并标记为 `ABSORBED`，不形成用户欠额。

2.5 倍定价对应直接模型成本口径下 60% 的毛利空间，用来覆盖支付通道、退款、税费、失败请求、基础设施和客服。它不是公司最终净利润率，价格快照和倍率必须进入每笔用量记录，便于日后审计。

## 4. 钱包、解锁与对账

- 充值菇点与活动赠送菇点分桶；消费优先扣赠送，再扣充值余额。
- 钱包余额是当前读模型，`wallet_ledger` 是追加式审计记录。支付回调、活动奖励、功能解锁和 AI 用量均使用唯一幂等键。
- 功能权限以 `billing_feature_entitlements` 的有效记录为准，不依赖本地存储或前端页面状态。
- 微信支付 V2 回调必须验证 API 密钥签名，并核验商户号、应用 ID、币种和订单金额后才入账；若切换 API v3，则必须验证微信支付公钥/平台证书签名、时效与 AES-GCM 通知资源。
- 前端支付成功只代表收银台流程结束。服务端会主动向微信查询订单，只有微信返回 `SUCCESS` 且全部字段核验通过才入账；异步通知是另一条幂等确认路径。
- 每个预支付订单 30 分钟失效，查单确认到期仍未支付时主动关单。商户订单号、微信交易号和钱包入账流水均有唯一约束，重复点击、重复查单和重复回调不会重复增加菇点。
- 「带走我的数据」包含钱包余额、流水、活动奖励、功能权益、充值订单、退款申请、协议接受和 AI 实际扣费字段，但不导出支付预下单载荷或付款人标识散列。

## 5. 协议与退款

注册时必须同意当前用户协议和隐私政策。首次充值、功能解锁或收费 AI 调用前，还必须明确同意当前收费与退款规则，接受版本和时间保存在 `legal_acceptances`。注册同意与收费同意保存为两个独立审计事件，不能相互冒充。H5 与小程序都提供独立于充值渠道的同意入口；法定主体、资质或协议尚未发布时，服务端拒绝保存收费同意。

用户可对仍显示为可退的未消费充值余额提交退款申请。以下项目不属于未消费充值余额：活动赠送菇点、已发生的 AI 调用成本、已履约且按已展示规则不支持无理由退回的数字功能。退款提交后冻结对应余额；运营审核后，系统先主动查验微信原订单，再按原订单拆分并使用唯一退款单号发起原路退款。只有微信退款回调或退款查单确认 `SUCCESS` 后才扣减充值余额并写退款流水。`PROCESSING` 和 `ABNORMAL` 都保持冻结，不能把“已受理”展示成“已到账”。

运营处理命令：

```bash
cd server
npm run billing:refund -- <退款申请UUID> process <处理人标识>
npm run billing:refund -- <退款申请UUID> reject <处理人标识> "未通过原因"
```

第一次执行 `process` 表示该处理人审核通过并发起退款，处理人标识与决定时间进入审计记录；微信仍在处理时，使用同一命令按原退款单号查单，不生成新的退款请求。争议、未成年人充值、重复扣款或服务未履约按适用法律和支付渠道规则优先处理。

协议正文由 `/api/billing/v1/legal/:key` 提供；法定主体或客服方式未配置时页面明确标记为未发布，不得用内部项目名替代合同主体。

## 6. 生产启用门槛

默认 `BILLING_MODE=disabled`：旧功能不因未配置收费而被误锁，也不接受支付。验收计费权限和 UI 时使用 `preview`；只有以下条件全部满足才可使用 `live`：

- `BILLING_MERCHANT_LEGAL_NAME` 是真实完整的收款法定主体；
- `BILLING_INVOICE_LEGAL_NAME` 与收款主体逐字一致；
- `BILLING_MERCHANT_ADDRESS` 是可公示的真实经营地址；
- `BILLING_CUSTOMER_SERVICE` 是用户可用的客服/退款联系方式；
- 正式客服邮箱为 `contact@extremenomad.org`，微信为 `evox077`；
- 2026-09-15 修正客服邮箱后，收费协议版本更新为 `2026-09-15-3`，用户需对修正后的联系方式重新确认；
- `WECHAT_PAY_MERCHANT_LEGAL_NAME` 必须记录微信商户平台显示的实际商户主体，并与服务、开票主体逐字一致；不一致时服务器强制关闭真实充值；
- `BILLING_APP_FILING_NUMBER` 仅在发布原生 APP 时填写，不作为 H5 收款门槛；
- `BILLING_ICP_QUALIFICATION` 已真实取得并与运营主体一致；如业务依法需要 ICP 许可证或其他前置许可，不能用普通备案号替代；
- 协议、价格展示、退款执行、开票路径和微信商户经营类目已经人工复核后，才设置 `BILLING_LEGAL_REVIEW_CONFIRMED=true`；
- `suyetiyu` 的商户号、公众号 AppID、V2 API 密钥、商户证书与私钥、支付 HTTPS 回调地址齐全；
- 公众号网页授权域名和 JSAPI 支付授权目录覆盖 `shroom.evox.run`，并设置 `WECHAT_PAY_PROTOCOL=v2_jsapi`、`WECHAT_PAY_JSAPI_ENABLED=true`；
- 微信支付商户平台中绑定的公众号 AppID、经营类目、实际开票主体和上述配置一致；
- 已按顺序执行 `036_billing.sql`、`037_payment_operations.sql`，并完成支付成功、主动查单、重复回调、金额篡改、余额不足、活动幂等、功能重复解锁、退款申请、退款回调和个人数据导出验收；
- 财务能够按支付订单、钱包流水、AI 用量事件和退款申请进行日结对账。

部署后运行 `cd server && npm run billing:check`。只有输出中 `ok: true` 和 `channels.H5.live: true` 才允许开放 H5 充值入口。

生产环境除支付/退款回调外，应使用单实例定时任务每 5 分钟运行一次 `cd server && npm run billing:reconcile`，主动补查最近待确认的支付、关闭已超时未支付订单，并补查已经审核发起的退款。命令本身不审核新的 `REQUESTED` 退款，也不会用新单号盲目重试结果不确定的退款。

## 7. 支付渠道边界

- **H5：** 仅支持在个人微信内打开菇日记并使用 JSAPI 支付。系统浏览器与企业微信不开放充值；支付完成后仍以服务端签名回调或主动查单为准，前端结果不能直接入账。
- **微信小程序：** 菇点、AI 调用和功能解锁属于虚拟服务。当前代码明确禁用普通 `requestPayment`，小程序包不展示充值按钮，也不引导到 H5 付款。只有运营主体在微信公众平台开通并审核通过“小程序虚拟支付”，取得真实接口参数并完成独立验收后，才能新增该渠道。
- **其他渠道：** 当前未实现支付宝、银行卡、App Store 或人工转账。不得通过线下转账后手工加点绕过订单、协议、开票和退款流水。
