# 人生 OS 长期事项层

## 定位

长期事项层把日记里的真实计划、行动、结果、观察和困惑，连接到 20 项可编辑的长期事项。它不是每日打卡、评分系统或项目管理器。

Shroom 现有两个人生 OS 层次，职责不同：

- **长期事项层**：回答“哪些事情值得长期维护，这周下一步是什么”。入口为日记首页的“人生 OS”。
- **判断原则层**：回答“什么才叫更好”。原则由 AI 提议、用户确认签发并保留版本，从长期事项页进入“判断原则与版本”。

菇卡继续保存具体时刻可复用的理解，待办继续保存具体行动，困惑与健康观察继续保存跨时间问题。长期事项只引用这些对象，不复制原始业务资料。

## 数据与隐私

迁移 `server/sql/022_life_os_long_term.sql` 新增：

- `life_os_items`：用户自己的 20 项模板、最低行动、当前下一步、优先级和维护状态；`stable_key` 固定为 `01`–`20`。
- `life_os_week_focus`：每周最多 3 项关注，不改变其余事项状态。
- `life_os_item_links`：日记关联及逐字证据，区分 `PLAN / ACTION / RESULT / OBSERVATION / INQUIRY`。
- `life_os_item_refs`：对已有待办、菇卡、困惑或外部资产的引用。
- `life_os_item_history`：用户编辑前快照。
- `life_os_weekly_reviews`：AI 草稿、用户确认版本和来源标识。

所有查询以登录会话中的 `user_id` 隔离。模块没有公开接口，也不会进入发现。专用导出只包含事项、必要关联摘要、引用、调整历史、已确认原则和每周复盘，不包含无关日记全文。

## 初始化与可靠性

首次读取长期事项接口时，服务端按稳定 ID 为当前用户补齐模板；重复进入使用唯一约束去重，不覆盖用户修改，也不批量修改其他用户。

日记 AI 分析沿用已有 follow-up 调用，一篇最多返回 3 条关联，原文依据必须能在日记正文中逐字找到。重复分析先替换尚未被用户纠正的 AI 关联，数据库唯一约束提供第二层去重。

日记修改或删除时：

- 未经用户纠正的 AI 关联直接删除；
- 用户纠正过的关联保留，但标记 `INVALID_SOURCE`，避免把旧证据继续当作有效来源；
- 日记保存本身不依赖人生 OS 分析成功。

AI 关联不创建或完成待办，不签发原则，不修改长期方向或优先级。每周复盘仅在用户主动发起时调用模型，先保存为可编辑草稿；确认后才进入历史，并把用户选中的最多 3 项写入下周关注。

## 页面与 API

- `/pages/shroom/life-os-plan`：本周关注、五个折叠板块、最近记录、复盘和导出。
- `/pages/shroom/life-os-item?key=01`：单项编辑、日记证据、已有对象/外部资产引用、调整历史。
- `/pages/shroom/life-os-weekly`：生成、编辑和确认每周复盘。
- `/api/life-os/v1/plan/*`：全部为登录后私有 API。

## 迁移与验证

部署前按编号执行 SQL：

```bash
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f server/sql/022_life_os_long_term.sql
```

基础验证：

```bash
npm --prefix server test
npm run build:h5
npm run build:mp-weixin
npm run build:app-plus
```

上线后用两个隔离账号验证首次初始化、重复进入、权限隔离、1–3 项关注、日记重分析去重、日记修改失效、复盘草稿确认和 JSON/Markdown 导出。
