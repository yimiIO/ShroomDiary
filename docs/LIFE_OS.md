# Shroom 人生 OS：产品与实现规范

> 状态：v1 已实现并部署
>
> 更新：2026-09-09
>
> 本文是人生 OS 的产品语义、AI 行为、数据模型和验收标准的共同依据。

## 1. 一句话定义

人生 OS 是用户此刻主动签发的少量判断标准：它帮助用户决定，对自己而言什么才叫“更好”。

它应当随着真实经历持续修订，但不会被 AI 静默改写。

> 菇卡帮助我在具体时刻做得更好。
>
> 人生 OS 帮助我决定什么才叫“更好”。

## 2. 为什么它必须与菇卡区分

菇卡和人生 OS 都来自经历，也都可能包含理解，因此最容易越做越像。区分它们的标准不是文字长短，而是使用层级：

| 判断 | 菇卡 | 人生 OS |
|---|---|---|
| 使用范围 | 一个或一类相似时刻 | 跨情境的选择与取舍 |
| 核心问题 | 下次遇到时，我想带着什么理解？ | 什么结果、关系和状态对我才算更好？ |
| 数量 | 可以随生活积累 | 必须少而有效，建议 5–9 条，当前最多 50 条 |
| 生命周期 | 收藏、复用、补充使用记录 | 保持、改写、合并、降级观察、退休并签发新版本 |
| 是否行动 | 不是 | 也不是 |
| 是否需要用户签发 | 创建需要确认 | 任何生效变化都需要确认 |

一个判断若高度依赖特定人物、场景或触发时刻，应留作菇卡。只有它确实能约束多种场景中的选择，且用户愿意认领，才适合成为人生 OS。

例子：

- “对方沉默时，不要立刻把它解释为否定。”更像一张关系情境菇卡。
- “重要关系中的清晰与尊重，比暂时避免冲突更重要。”可以是人生 OS 的判断标准。
- “明天给对方打电话。”是待办，不属于前两者。

## 3. 四层模型

```text
经历层：日记保存发生过什么
理解层：菇卡保存在相似时刻可复用的理解
标准层：人生 OS 保存跨情境的判断标准
行动层：待办/实验保存接下来具体做什么
```

“模式候选”是跨越经历层与标准层的内部观察状态：系统怀疑某种模式存在，但证据或用户认同尚不足。它有价值，因为能防止 AI 过早给用户贴标签；它不需要成为一级产品中心。

模式候选只能以这些形式出现：

- 回看回答中的“可能存在，但证据仍不足”；
- 人生 OS 提案中的“继续观察”；
- 原则上的 `emerging` 状态、支持依据和反例。

## 4. 目标与非目标

### 4.1 目标

- 把旧式、越积越长的人生 OS 整理成少量独立原则。
- 让用户看懂为什么保留、合并、改写、转为菇卡或退休。
- 保存每条原则的形成方式、证据、反例和历史版本。
- 让用户可以修改、拒绝或延后任何 AI 建议。
- 让新经历能够触发复查，而不是自动制造新原则。

### 4.2 非目标

- 生成完整人格画像、心理诊断或固定身份标签。
- 从单篇强烈日记直接推断长期价值观。
- 把所有菇卡提升为人生 OS。
- 把人生 OS 变成待办列表、行为打卡或效率系统。
- 追求原则数量、AI 生成频率或版本数增长。

## 5. 原则结构

每条生效原则包含：

| 字段 | 含义 |
|---|---|
| `area` | 原则所属生活领域，用于阅读组织，不是僵硬分类 |
| `principle` / `statement` | 用户当前认可的判断标准 |
| `boundary` | 它不适用或需要让位的条件 |
| `reviewQuestion` | 未来判断它是否仍有效的问题 |
| `basis` | `chosen` 主动选择、`observed` 经历中形成、`mixed` 两者共同形成 |
| `confidence` | `high` 稳定、`medium` 较稳定、`emerging` 待观察 |
| `sourceRefs` | 支持它的本人日记或本人菇卡 |
| `counterSourceRefs` | 挑战它、提示边界或反例的本人日记/菇卡 |
| `supersedes` | 本条替代、合并或改写了哪些旧原则 |
| `snapshotVersion` | 它属于哪一个已签发版本 |

“主动选择”与“从经历观察到”必须分开。一个人想成为怎样的人，不应该因为过去出现次数较少就被 AI 否定；一个反复出现的行为，也不因此自动成为用户认可的价值观。

## 6. 数量与淘汰规则

- 理想生效数量：**5–9 条**。
- 当前生效硬上限：**50 条**。这是容量保护，不代表鼓励积累到 50 条。
- 达到上限后，整理流程必须优先合并、降级或退休，不能继续追加。
- 每条原则至少应有清晰的使用范围；同义原则合并为一条，具体情境内容转为菇卡。
- 暂时矛盾的证据可以共同保留为“仍在观察”，不要求 AI 强行得到一致结论。
- 退休不等于删除。旧原则与旧版本必须可回看，以解释人的变化。

## 7. 生成与修订流程

### 7.1 首次生成

用户可以选择两种入口：

1. **从自己的记录生成探索版**：当至少有 3 个有效日记日，AI 比较日记与本人菇卡，提出候选原则。
2. **亲自写下第一条原则**：无需 AI 推断，形成 `chosen + emerging` 的待确认条目。

旧系统已有整篇 Markdown 人生 OS 时，先执行一次“整理并精简现有 OS”，将原文拆成可独立维护的原则。旧原文完整保留，在签发前不会变化。

### 7.2 复查触发

当前实现会在工作区给出复查建议，满足任一条件即可提示：

- 还没有签发第一版；
- 当前仍是未结构化的旧版文档；
- 上次签发后积累至少 3 个新的日记日；
- 上次签发后积累至少 3 张新菇卡；
- 当前版本超过 90 天未复查。

触发只显示建议，不自动调用 AI。用户明确点击后，系统才发送允许 AI 使用的数据并生成新提案。

这些阈值是当前产品假设，不是永恒规则。后续应依据用户是否认为建议及时、是否频繁忽略来校准。

### 7.3 AI 整理动作

AI 对当前原则和新证据只能提出以下变化：

- `keep`：继续保留；
- `rewrite`：保持含义但改清楚边界或表达；
- `merge`：把重复或上下级原则合并；
- `move_to_card`：过于具体，建议留作菇卡理解；
- `observe`：证据冲突或不足，继续观察；
- `retire`：当前已不再适合或被更高质量原则替代。

AI 必须同时说明变化原因，并保留支持材料与反例。它不能因追求整齐而消除真实矛盾。

### 7.4 用户审核

提案页面必须允许用户：

- 查看整理前与拟生效数量；
- 逐条纳入或排除；
- 修改判断标准、适用边界和复盘问题；
- 看见形成方式、稳定程度、支持依据和反例；
- 查看“为什么这样整理”的全部变化解释；
- 单独选择是否把某个具体理解创建为私密菇卡；
- 放弃整份提案并保留当前版本。

待确认提案不是人生 OS。只有点击“确认签发”后才生效。

### 7.5 签发

服务端在事务中完成：

1. 锁定提案并核对归属、状态和基础版本；
2. 校验客户端只能编辑服务端提案中存在的条目；
3. 校验最终原则为 1–50 条；
4. 再次校验所有日记/菇卡来源属于当前用户；
5. 生成新的整篇 Markdown 快照与 `life_os_versions` 记录；
6. 把上一版结构化原则标记为退休，写入新版本原则和证据关系；
7. 只为用户明确勾选的建议创建私密菇卡；
8. 将提案标记为已接受。

如果基础版本已在另一设备改变，返回冲突，不覆盖新版本。

## 8. 自动化权限矩阵

| 行为 | 可以自动 | 需要用户操作 | 禁止 |
|---|---:|---:|---:|
| 计算“是否建议复查” | ✓ |  |  |
| 在页面解释触发原因 | ✓ |  |  |
| 调用 AI 读取允许分析的日记 |  | ✓ |  |
| 生成待确认整理提案 |  | ✓ |  |
| 修改提案文字或选择条目 |  | ✓ |  |
| 签发新人生 OS |  | ✓ |  |
| 从建议创建私密菇卡 |  | ✓，且默认不选 |  |
| 公开人生 OS 或菇卡 |  | ✓，另行明确选择 | AI 不得代替选择 |
| 自动修改、删除或签发人生 OS |  |  | ✓ |
| 把观察到的行为称为用户价值观 |  |  | ✓ |

## 9. 数据模型

### 9.1 权威快照

- `life_os`：当前整体 Markdown 快照与版本号，兼容既有客户端和导出。
- `life_os_versions`：每次签发的不可追溯改写历史，保存来源、生成方式和生成元数据。

### 9.2 结构化原则

- `life_os_clauses`：每个版本的独立原则、边界、复盘问题、形成方式、状态、顺序和前序关系。
- `life_os_clause_evidence`：原则到本人日记/菇卡的支持或挑战关系。

### 9.3 审核提案

- `life_os_review_proposals`：待确认、已接受、已拒绝或被新提案取代的结构化建议。
- `base_version` 防止跨设备覆盖；`payload` 保留 AI/人工提案的结构；`result` 保存最终签发结果。

来源引用是审计与解释材料，不是新的业务数据源。日记和菇卡仍然各自是权威记录。

## 10. API 契约

所有接口均要求已认证用户，用户身份只来自会话或受限 API Token。

| 方法与路径 | 用途 |
|---|---|
| `GET /api/life-os/v1/workspace` | 返回当前配置、结构化原则、最近待确认提案、复查信号和数量策略 |
| `POST /api/life-os/v1/review/draft` | 用户主动调用 AI，生成并保存待确认整理提案 |
| `POST /api/life-os/v1/review/manual` | 从当前原则进入逐条人工编辑，或开始第一条主动选择原则 |
| `POST /api/life-os/v1/review/:id/publish` | 以用户最终选择和编辑后的条目签发新版本 |
| `POST /api/life-os/v1/review/:id/reject` | 拒绝提案，当前版本不变 |
| `GET /api/life-os/v1/config/history` | 分页查看历史签发版本 |
| `GET /api/life-os/v1/config` | 兼容读取整体 Markdown 配置 |
| `PUT /api/life-os/v1/config` | 兼容旧客户端的整体保存；会退休当前结构化原则并关闭待确认提案 |
| `POST /api/life-os/v1/draft` | 旧版 AI 草稿接口，保留兼容；新 UI 使用 review 流程 |

新客户端应使用 `workspace + review` 接口，不应把整篇 Markdown 编辑作为默认路径。

## 11. AI 上下文与输出规则

输入范围：

- 当前用户的人生 OS 与当前结构化原则；
- 当前用户最近最多 120 篇、正文非空、未删除且允许 AI 使用的日记；
- 当前用户最近最多 80 张菇卡；
- 不读取他人的公开卡来定义当前用户。

输出要求：

- 优先精简而不是增加；
- 区分用户主动选择与从经历观察到；
- 长期判断需要多条真实输入支持，证据不足时标记待观察；
- 引用只能使用输入中的来源键，服务端再映射并验证真实所有权；
- 主动寻找反例、边界和时间变化；
- 不做人格、疾病、创伤或关系诊断；
- 菇卡建议必须是理解、提醒或观察视角，不能写成行动、待办或承诺；
- 返回严格结构化 JSON，服务端再次归一化和截断。

## 12. 隐私、安全与失败策略

- 只有 `ai_allowed = true` 的日记进入 AI 上下文。
- AI 提案按用户隔离，来源在签发时再次验证所有权。
- 人生 OS 默认私密，没有公开 API 或发现入口。
- AI 不可用、超时或输出无法归一化时，当前版本保持不变。
- 发布事务任一步失败都不得产生半个新版本。
- 删除日记或卡片时，历史快照可以保留当时的文字，但结构化引用必须遵循数据库外键与导出隐私策略。
- 产品文案不应把“稳定”表达为科学证明，只代表当前材料下的使用状态。

## 13. UI/交互验收

- 首屏必须解释菇卡与人生 OS 的区别，并显示当前数量、待确认提案和上限。
- 旧版内容存在时必须可查看原文，整理前不可丢失。
- 生成过程显示任务阶段、估算进度和已用时间，并说明当前版本不会被覆盖。
- 每条提案可单独编辑、纳入或排除；长文本在 H5、App 和小程序均不横向溢出。
- “建议留作菇卡”明确写出“菇卡不是行动，默认不会创建”。
- 签发前二次确认版本号、原则数量和将创建的私密菇卡数量。
- 拒绝提案后当前人生 OS 不变。
- 历史版本可回看，且显示生成方式与来源数量。

## 14. 已实现与后续候选

### 14.1 已实现（2026-09-09）

- 数据库迁移 `014_life_os_generation.sql` 与 `015_life_os_evolution.sql`。
- 结构化原则、正反证据、审核提案、签发与拒绝 API。
- 用户触发的 DeepSeek/OpenAI-compatible JSON 整理流程。
- 旧 Markdown 兼容与整理入口。
- 5–9 条建议、50 条服务端硬上限。
- 个人中心数量提示、提案审核 UI、可选私密菇卡和版本历史。
- 数据导出纳入原则与提案。
- 单元/契约测试、H5 生产构建与生产 API 闭环验证。

### 14.2 后续候选（尚未实现承诺）

- 后台持续提取模式候选，但只在复查时聚合展示。
- 按单条原则查看完整来源原文、时间线和反例变化。
- 按条恢复或选择旧版原则重新进入提案，而不恢复整篇快照。
- 依据用户真实采纳/忽略行为调整 3 天、3 卡、90 天触发阈值。
- 把人生 OS 对真实选择的帮助做成用户自评，而不是自动评分或行为规训。

任何候选开发都必须继续满足一条底线：AI 可以帮助用户看见变化，但不能替用户决定自己是谁、什么值得追求。
