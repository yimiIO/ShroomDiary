# Shroom API

Independent Node.js/PostgreSQL service for Shroom. It contains Shroom's own
wallet, AI usage charging and WeChat Pay boundary, but no mall, distribution,
course, school, or surfing domain.

Runtime configuration is provided only through environment variables:

- `DATABASE_URL`
- `TOKEN_SECRET`
- `ACCESS_TOKEN_SECONDS` (defaults to `7200`)
- `REFRESH_TOKEN_DAYS` (defaults to `90`)
- `PORT` (defaults to `3102`)
- `PUBLIC_ORIGIN`
- `ALLOWED_ORIGINS` (optional comma-separated transition origins)
- `UPLOAD_DIR`
- `COS_BUCKET`, `COS_REGION`, `COS_SECRET_ID`, `COS_SECRET_KEY` (private image storage)
- `COS_REQUIRED_FOR_IMAGES=true` (production fail-closed setting)
- `IMAGE_MAX_PIXELS` (defaults to `40000000`)
- `IMAGE_MAX_DIMENSION` (defaults to `1600` for photo-like uploads)
- `STATIC_DIR`
- `ASR_API_BASE_URL`, `ASR_API_KEY`, `ASR_MODEL` (optional; all three are required to enable transcription)
- `ASR_LANGUAGE` (defaults to `zh`)
- `ASR_TIMEOUT_MS` (defaults to `120000`)
- `AI_API_BASE_URL`, `AI_API_KEY`, `AI_MODEL` (optional; all three are required to enable five-view analysis)
- `AI_TIMEOUT_MS` (defaults to `120000`)
- `EMBEDDING_API_BASE_URL`, `EMBEDDING_API_KEY`, `EMBEDDING_MODEL`,
  `EMBEDDING_DIMENSION` (optional as a group; OpenAI-compatible embeddings API)
- `EMBEDDING_PROVIDER` (provider label stored in the immutable embedding profile)
- `EMBEDDING_TIMEOUT_MS`, `EMBEDDING_BATCH_SIZE`
- `MEMORY_WORKER_ENABLED`, `MEMORY_WORKER_INTERVAL_MS`
- `FRIEND_SYNC_WORKER_ENABLED`, `FRIEND_SYNC_WORKER_INTERVAL_MS`
- `DAILY_REVIEW_WORKER_ENABLED`, `DAILY_REVIEW_WORKER_INTERVAL_MS`
- `DAILY_REVIEW_EMAIL_HOUR`（默认上海时间 `22`）
- `MAIL_SMTP_HOST`, `MAIL_SMTP_PORT`, `MAIL_SMTP_SECURE`
- `MAIL_SMTP_USER`, `MAIL_SMTP_PASSWORD`, `MAIL_FROM`
- `COMPOUND_STATS_URL`, `COMPOUND_STATS_USERNAME`, `COMPOUND_STATS_PASSWORD`
- `COMPOUND_STATS_TIMEOUT_MS`（默认 `8000`）
- `BILLING_MODE`（`disabled` / `preview` / `live`，默认 `disabled`）
- `BILLING_MERCHANT_LABEL`（内部标签，默认 `suyetiyu`；不能代替法定主体）
- `BILLING_MERCHANT_LEGAL_NAME`, `BILLING_INVOICE_LEGAL_NAME`, `BILLING_MERCHANT_TAX_ID`
- `BILLING_MERCHANT_ADDRESS`, `BILLING_CUSTOMER_SERVICE`
- `BILLING_ICP_QUALIFICATION`, `BILLING_APP_FILING_NUMBER`
- `BILLING_LEGAL_REVIEW_CONFIRMED`（主体、资质、协议、退款、开票和商户类目人工复核后才设为 `true`）
- `BILLING_AI_CHARGE_MULTIPLIER`（默认 `2.5`）
- `BILLING_AI_MINIMUM_START_POINT_CENTS`（默认 `1`，即开始调用至少有 0.01 菇点）
- `WECHAT_PAY_H5_ENABLED`, `WECHAT_PAY_MCH_ID`, `WECHAT_PAY_APP_ID`
- `WECHAT_PAY_MERCHANT_SERIAL`, `WECHAT_PAY_PRIVATE_KEY_PATH`, `WECHAT_PAY_API_V3_KEY`
- `WECHAT_PAY_PUBLIC_KEY_ID`, `WECHAT_PAY_PUBLIC_KEY_PATH`（推荐），或 `WECHAT_PAY_PLATFORM_CERT_PATH`
- `WECHAT_PAY_NOTIFY_URL`, `WECHAT_PAY_REFUND_NOTIFY_URL`, `WECHAT_PAY_TIMEOUT_MS`

Private diary media is never exposed as a static directory. Each asset belongs to
one Shroom user and is read through a short-lived signed URL regenerated by diary
responses.

New diary images are decoded on the Shroom server, corrected for EXIF orientation
and stripped of EXIF/GPS metadata before upload to the private Shroom COS bucket.
Transparent graphics first try lossless WebP. Photos use adaptive high-quality
WebP with a 1600px maximum edge. The encoder selects the highest candidate that
does not exceed the incoming file size, so a "compressed" object is never larger
than its source. Already-smaller, metadata-safe assets may be preserved instead
of being enlarged. The temporary original and processing file are deleted after
the COS write. COS credentials stay server-side and clients use the same Shroom
media URL on H5, App and mini-program builds. Voice files remain in the private
local media directory until their storage policy is migrated separately.

Voice recordings are stored as private Shroom media first. Transcription stays
disabled until the operator explicitly chooses and configures an ASR provider.
When enabled, transcription is initiated by the user and sends only the selected
recording to that provider. The returned text remains an editable draft until
the user inserts it into the diary body and saves.

Apply the numbered files in `sql/` in order with the dedicated Shroom database
role, then run `npm start`. Production deployment uses a systemd
unit and binds the application to localhost; Nginx is the only public entry
point.

Billing remains fail-closed until `BILLING_MODE=live`, the collection and invoice
legal names match exactly, public qualifications/contact fields are complete, the
operator confirms legal review, and every WeChat Pay credential/file/HTTPS callback
passes runtime validation. Run `npm run billing:check` before opening payments.
Standard H5 payment is only enabled outside WeChat; standard Mini Program
`requestPayment` is intentionally blocked for Shroom's virtual services.
Run one non-overlapping `npm run billing:reconcile` job every five minutes in
production to actively verify pending payments and already-approved refunds.

Migrations `036_billing.sql` and `037_payment_operations.sql` add separate
paid/reward balances, an append-only wallet ledger, feature entitlements,
campaign rewards, payment/refund records, agreement acceptances, AI charge
fields, active payment reconciliation and original-path refund items. Operator-reviewed refunds use the
original WeChat orders:

```bash
npm run billing:refund -- <refund-request-uuid> process <operator>
npm run billing:refund -- <refund-request-uuid> reject <operator> "review note"
```

See `../docs/BILLING.md` before enabling production payments.

Diary reflection uses PostgreSQL + pgvector. Diary text remains authoritative;
chunks, vectors and analyses are derived records. See
`REFLECTION_ARCHITECTURE.md` for the consistency, privacy, backfill and rollback
contract.

Saving a new or changed AI-allowed diary also queues a private people sync. The
model may identify only people and verbatim evidence present in that diary. Code,
not the model, maps approved rule codes to score changes. Interaction, score and
promise writes are versioned and idempotent; editing, deleting, or revoking AI
access reverses the previous auto-applied effects before another version can run.

Browser sessions use short-lived access tokens plus rotating refresh tokens.
The client coordinates concurrent 401 responses through one refresh attempt so
several page requests cannot consume the same one-time token independently.
Trusted personal agents use separately revocable, hashed and resource-scoped API
tokens from `api_tokens`; never put an account password or browser refresh token
in an agent configuration file.

User-level external data sources are separate from both personal Agent tokens and
the Compounding System. The first connector is Codex: under
`My -> Data & Connections -> Codex`, the user copies one short-lived connection
instruction to Codex. That instruction installs the official `shroom-codex`
connector and pairs it without a separate code-copy step. The connector uses Codex
app-server over stdio and sends only redacted task metadata. Shroom never accepts a
caller-supplied user id for these writes and stores only a hash of the connector
token. After pairing once, the macOS connector installs a user LaunchAgent that
runs at 19:00 and is also loaded when the user session starts. A missed run is
recovered after startup or wake, and the incremental cursor backfills omitted
tasks without duplicating them. See
`../docs/DATA_SOURCES.md` for the collection, deletion, export and AI-use contract.

Daily review is a derived, source-referenced draft under `/api/daily-reviews/v1`.
Opening it in Shroom creates or refreshes the review and marks it viewed. At 22:00
Shanghai time, the worker sends an unviewed review only when the user has verified
an email address and explicitly enabled private email delivery. SMTP is fail-closed:
without the complete mail configuration, web reviews continue to work and no mail
is sent. Migration `038_daily_reviews.sql` stores review provenance, view state,
email consent and an idempotent delivery state.

See `STORAGE.md` for the single-source storage boundary and the distinction
between runtime data and one-time migration inputs.

The temporary `shroom.surfplus.xyz` production topology keeps the API and
PostgreSQL database on the independent Shroom server. The Surfplus host serves
only the H5 bundle and forwards `/api/` through the restricted
`shroom-api-tunnel.service`; the tunnel key is limited to local port 3102 and
cannot open a shell. DNS must contain only the edge address while this topology
is active.

Life OS review uses the configured AI provider only after an authenticated user
explicitly starts it. The server selects that user's own AI-allowed diary entries,
cards and current clauses, then creates an editable pending proposal. The review
can keep, rewrite, merge, move concrete understanding to a card, leave tension
under observation, or retire an old principle. It never saves or replaces Life
OS automatically. Only a user-confirmed publish creates the next snapshot and
active clauses; every support/challenge reference is revalidated as belonging to
the same account. See `../docs/LIFE_OS.md` for the full contract.

The current Compounding System is mounted at `/api/compound/v2` for every
authenticated user. It begins with a shared, versioned archetype catalog, then
persists each user's private mapping, four-week validation state, twelve-week
plan, principal/return metrics, time allocation, blockers, real results, diary
reviews, and evidence-linked stage reviews. It may read confirmed Life OS
clauses as context but cannot modify them. The old
owner-only `/api/compound/v1` four-account endpoint and its
`compound_settings`/`compound_checkins` records remain available only for
backward compatibility and export. Neither API accepts a client-provided user
identifier. See `../docs/COMPOUND_SYSTEM.md`.

With the account owner's explicit authorization, legacy diaries can be scanned
once for unresolved-question candidates without rerunning the full five-view
analysis for every entry:

```bash
npm run backfill:inquiries -- --mobile=13800000000 --apply
```

The command reads only AI-allowed text diaries owned by that exact account,
records provider usage, and writes pending candidates. It never creates a formal
inquiry until the user confirms it in the product. Re-running against existing
pending historical candidates requires the explicit `--replace-pending` flag.
